# v25.3 — what changed in this round

Install as usual, then **restart both processes**. Confirm you are on the new build:

```
curl http://localhost:5001/api/_version
```

It returns `{"build":"v25.3", ...}` and the full list of mounted routes. The server
also prints a banner at boot. If the build is not `v25.3`, you are talking to a
stale process — that alone explains a "route not found".

---

## 1. "Route not found: GET /api/document-templates/types"

I booted the real `app.js` and called the endpoint. It returns **401 Missing
authorization token**, not 404 — the route was mounted correctly all along. Your
running server was the old process.

To make that diagnosable rather than a guessing game, all 21 routers now mount from
a single `ROUTE_TABLE` in `app.js`, and `GET /api/_version` reports that exact table.
The version endpoint can no longer drift from what is actually mounted.

## 2. Holiday on 15 Aug displayed on the 14th

A real bug, and a systemic one. Code did:

```js
startOfDay(date).toISOString().slice(0, 10)
```

`startOfDay` works in **server-local** time (`setHours`), `toISOString` converts to
**UTC**. On an IST server those disagree by 5h30m:

```
stored              2026-08-15T00:00:00.000Z
startOfDay (IST)    2026-08-14T18:30:00.000Z
key produced        "2026-08-14"   <-- shown to you
```

Every calendar-day key in the app was built this way — **7 occurrences across 4
files**, so it also meant regularization clicks posted the wrong date. Replaced with
`dateKey()` (formats from local parts) and `calendarDay()` (reads a date-only value
as a local calendar day). Verified correct under both IST and UTC server clocks.

While fixing this the automated edit briefly produced `function dateKey(date){ return
dateKey(date); }` — infinite recursion — in two services. Both were caught by booting
the app and are removed.

## 3. Working on a holiday is now visible

The punch was recorded but the calendar painted a flat `H`, so the day looked like
nobody came in. Days now carry `isHoliday`, `workedOnHoliday` and
`holidayWorkMinutes`, and the calendar letter becomes **`H+`** when someone actually
worked a holiday.

## 4. Gemini could not grant payroll access

`CHANGE_ACCESS_SCOPE` was fully implemented; the **classifier** never reached it:

```js
/(?:access|visibility).*(?:office|factory|selected)/i
```

"give access to Aindrila can view the payroll" contains *access* but none of
*office/factory/selected*, so it fell through to `UNKNOWN`. The classifier now
recognises grant/revoke phrasing across payroll, salary, attendance, leave and
profile. Checked against six phrasings, and against shift/leave/PF commands to
confirm it does not hijack other intents.

## 5. Payslip download in the employee portal

- **Server:** `GET /payroll/slips` now hides slips whose run is still `DRAFT` from
  non-admins. Previously an employee could see an unreleased slip.
- **Client:** a **My payslips** card on the account page — month, payable-vs-working
  days, LOP, net pay behind an eye toggle, and a PDF download button.

## 6. Home page scene did not change with the time of day

Two causes:

1. `const now = new Date()` ran **once at render** and never ticked. Open the tab in
   the morning and it stayed morning all night. There is now a `useNow()` hook that
   re-renders on the minute.
2. The palettes were nearly identical — morning/midday/afternoon used suns of
   `#ffd976`, `#ffd966`, `#ffd86f`. Even when the period changed, nothing looked
   different.

Six genuinely distinct palettes now, including a new **dawn** period: cool dawn,
fresh blue morning, bright midday, warm gold afternoon, burnt sunset, deep indigo
night. Lit windows appear at dawn/evening/night instead of only night.

## 7. Building a document from scratch

The create panel has two modes side by side — **Use a preset** and **Start from
scratch** (a genuinely empty page). You can name the document at creation. An empty
canvas shows a hint pointing at the block palette, and Preview refuses an empty
document rather than returning a blank PDF.
